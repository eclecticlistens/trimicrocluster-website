How TMC took shape.

The instrument grew through changes of direction as well as additions. These are some of the decisions that explain why it sounds and behaves as it does.

Keeping behaviour, changing sound

In the August discussions, TMC already had the beginnings of a distinct vocabulary. Anchor, Orbit and Shimmer described musical relationships. Still, Drift, Shine and Mix described behaviour. The Conductor coordinated activity across layers.

One important decision was more specific than simply adding another synth. Nick wanted to move away from the earlier Kal/Bell sound while retaining and reworking useful cell-memory behaviour. The sound and the idea behind its organisation did not have to stay together. Resonant Rings-based material became part of that continuing development.

On 17 August, the name TriMicroCluster was retained with the AOS triad explicitly included in its meaning. The project was beginning to be described through its own musical relationships, not only through the software from which some early experiments had grown.

Choosing what not to build

Research provided possibilities, not instructions that had to be followed. On 2 September, Nick asked to drop pulsar synthesis from the TMC direction because its results did not fit the musical purpose he wanted. A technique could be interesting and still be wrong for this instrument.

The same conversation expanded the listening and research interests to Autechre and Gerald Donald. Those interests helped define questions worth asking about sound creation and programming systems. They do not establish that a TMC algorithm was copied from either artist.

Two different uses emerged

By late September, it had become useful to distinguish a standalone instrument from a personal performance system. Core was the community-facing norns direction. Advanced was the environment in which external MIDI, percussion, recording and individual hardware choices could develop more freely.

The hardware conversations reveal why this distinction mattered. On 2 October, a complete stereo mix from norns alongside eight separate ES-8 stems was a requested routing target. At that point it was not an already verified change. A later article must not silently turn the request into proof that the routing was working.

A desired setup, a successful connection and a tested full system are three different milestones.

The current publication policy preserves that separation: Core is intended for public software release after preparation; Advanced can be documented without making its specialised implementation downloadable.

A listening decision: the Objects ensemble

The percussion work gradually concentrated on Objects rather than continuing the earlier Pulse and Fracture branches. The attraction was not simply a larger range of drum patterns. It was the possibility of independent motifs and changing participation that could sit within the larger TMC music.

On 20 October, the work had precise boundaries. Pad 8's Slicer behaviour was to be kept while Pads 1–6 were refined. Pad 7 remained unchanged for later manual exploration of its granular role. Protecting an accepted part of the system made it possible to judge the next change without moving every reference point at once.

There was also a practical constraint in the Slicer work: the slice count chosen in TMC had to agree with the Bitbox setup. An eight-slice example should therefore be described as a particular configuration, not as a universal hard-coded requirement.

The eight-slice baseline

The retained October baseline was documented with eight slices and the six-event sequence 1, 5, 3, 6, 5, 8. Those settings describe that listening example. They are not a statement of Bitbox factory behaviour, a guarantee of the latest code, or a required setting for every future sample.

Testing the actual system

The original aluminium norns and the shield did not always give the same result. Rings Cells testing exposed CPU and audio difficulties on the original unit that were not reproduced in the same way on the shield. That is a musical development issue as much as a technical one: a convincing idea is not ready for release if the intended hardware cannot sustain it.

The cleanup work also reported passing local tests. Those checks are valuable, but they answer a different question from an extended listening session or a run on an older compute module. The release record needs all three kinds of evidence, kept distinct.

Code checks

Did the particular conditions checked by the tests behave as expected?

Listening

Did the resulting music justify keeping the design?

Hardware

Could the identified device and software configuration run it reliably?

Release

Can another person install and use the documented version under the stated conditions?

Ideas still outside the instrument

A four-voice MIDI part discussed on 21 October belongs to the proposal stage of the record. Its direction was to reuse the existing Conductor and AOS thinking, without adding Grid nudges or another set of manual controls. It should not appear in a feature list merely because the idea was discussed in detail.

The wider reading around interactive instruments and computational creativity also has a life beyond TMC. Not every interesting paper needs to become a development task. Leaving room for curiosity is part of the process.

How this history is assembled

This article is based on selected August–October development conversations, including the early architecture, naming, research, routing and 20 October acceptance records. It is an editorial history, not a complete chat transcript or a release changelog. Exact claims about a particular implementation still need the corresponding code or test record.

The source set includes music and hardware conversations as well as the main TMC discussion. Decisions are dated where the recovered record is specific; broader changes are described as periods rather than assigned an invented day.
